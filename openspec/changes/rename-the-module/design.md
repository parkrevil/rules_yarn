## Context

See proposal.md (Why). Today the name `rules_yarn` does three jobs:

- **Module name.** `module(name = "rules_yarn")` in `MODULE.bazel`. Consumers
  and overrides name the module by it.
- **GitHub repository name.** `parkrevil/rules_yarn`. The release archive
  `rules_yarn-<tag>.tar.gz`, its prefix `rules_yarn-<version>`, and the `{REPO}`
  substitutions in `.bcr/source.template.json` all derive from it.
- **Project name in prose.** Comments, doc strings, error messages.

The ruleset names itself as `@rules_yarn` in two places that are not its own
repository. Both live in the repository that `yarn.install` generates:

- `yarn/private/install/node_modules.bzl` is symlinked into that repository
  and loaded from its root (`repository.bzl`, `repository_ctx.symlink`). Its
  `load("@rules_yarn//yarn:providers.bzl", ...)` and its two `Label("@rules_yarn//...")`
  defaults resolve there.
- The `BUILD.bazel` that `repository.bzl` (`_build_file`) writes loads
  `@rules_yarn//yarn:defs.bzl`.

Every other label inside `yarn/` that Bazel resolves is already relative, for
example `Label("//yarn/private/install:driver.js")` in `repository.bzl`. The
doc examples in `yarn/extensions.bzl` and `yarn/private/yarn_binary.bzl` name
`@rules_yarn`, but Bazel never resolves them: they are text addressed to
consumers.

## Goals / Non-Goals

**Goals:**

- Change only the module name. The repository name and the project name stay.
- After this change, the module name appears as a resolved label in only the
  two places that have no other way to refer to the ruleset. Elsewhere it
  appears only in text addressed to consumers.

**Non-Goals:**

- Renaming the GitHub repository. That would change archive names and URLs
  for no registry benefit.
- Keeping `rules_yarn` working as an alias for consumers.

## Decisions

### 1. The name is `parkrevil_rules_yarn`

The registry maintainer asked for "a user prefix". The registry's automated
review on #10979 suggested this exact form. A module named apart from its
repository is the registry's ordinary shape: `aspect_rules_js` is published
from `aspect-build/rules_js`.

The publishing workflow already copes with the two names diverging:

- publish-to-bcr v1.5.0 reads the module name from `MODULE.bazel`
  (`src/domain/module-file.ts:24-26`).
- It writes the entry under `modules/<module name>/`
  (`src/domain/create-entry.ts:87-99`).
- The reusable workflow `publish.yaml` calls it at commit `f9cfe7a`. That
  workflow titles the pull request from the action's `short-description`
  output (`.github/workflows/publish.yaml:399` at v1.5.0). The action sets
  that output to `<module name>@<version>`
  (`src/application/action/main.ts:86-90` at `f9cfe7a`).

The `{REPO}` substitutions keep resolving to the GitHub repository, so
`.bcr/` needs no change.

### 2. Self-references: relative where possible, the module name where not

Files in the ruleset's own repository keep using relative labels. `Label()`
resolves a relative label "in the context of the package where the calling
`.bzl` source file lives". That quote is from
`docs/versions/9.2.0/rules/lib/builtins/Label.mdx` in bazelbuild/bazel, at
commit `6bc0fe5`. The same rule is why the two generated-repository places
above cannot use a relative label: there, it names the generated repository.

Those two places therefore use `@parkrevil_rules_yarn`. This resolves through
two documented rules:

- A repository generated by a module extension "can see all repos visible to
  the module that hosts the extension" (`site/en/external/extension.md`,
  "Repository names and visibility", Bazel 9.2.0 and 8.3.0).
- A module sees its own repository under its module name: "By default, the
  name of the repo is the name of the module" (`ModuleFileGlobals.java:127-132`,
  `module(repo_name)`, Bazel 8.3.0).

**Alternatives considered:**

- **`module(name = "parkrevil_rules_yarn", repo_name = "rules_yarn")`** (same
  source). Every `@rules_yarn` inside the ruleset would keep working. The
  cost is that the module goes by two names, one of which only its own files
  use. The published API docs would not hide that. `yarn/BUILD.bazel` sets
  `render_main_repo_name = True` on each `starlark_doc_extract`, which renders
  the module's name, so the docs would show `@parkrevil_rules_yarn` while the
  ruleset's own files say `@rules_yarn`. Rejected.
- **Writing `str(Label("//yarn:defs.bzl"))` into the generated `BUILD.bazel`.**
  This is a supported way to name the ruleset's repository. It cannot cover
  `node_modules.bzl`, though, whose `load` must be a literal, so the same need
  would end up with two mechanisms. Rejected.

### 4. Release v0.2.0, pushed by hand as a lightweight tag

The change lands as a `feat!:` commit with a `BREAKING CHANGE:` footer. ccv
at the pinned commit `7318e2f` matches either form
(`^(fix|feat)(\(.+\))?!: |BREAKING CHANGE: `, `ccv.go:16`) and computes a
major bump (`ccv.go:137-139`), v1.0.0. `tag.yaml` leaves a major version to a
person ("Leave a major version to a person"), so no tag is written. The user
chose v0.2.0, the usual minor bump for a breaking change before 1.0.

The tag must be lightweight (`git tag v0.2.0 <merge sha>`, with no `-a` and
no `-s`). ccv maps each tag ref's own hash to the tag
(`tagRefs[r.Hash().String()]`, `ccv.go:91-94`) and matches commits against
that map. An annotated tag's ref points at a tag object rather than a commit,
so ccv would never find v0.2.0. It would walk back to v0.1.0, see the `feat!`
commit, and hold every later release at "major". `v0.1.0` is lightweight
(`git for-each-ref` reports `commit`).

Pushing the tag starts `release.yml`. It builds the release, calls
`publish.yaml` to open a draft registry pull request, then finalizes the
GitHub release. A later `tag.yaml` run starts from v0.2.0, so the `feat!`
commit behind it no longer counts.

### 5. README version

The README's examples move to 0.2.0 in the same change. Main then describes
a release that is one tag push away. Any other order leaves the README
naming a module (`rules_yarn` at 0.2.0) that never exists. The README's
`archive_override` example already uses an `integrity = "sha256-..."`
placeholder, so it needs no value from the release.

### 6. Canonical names in `install_scenarios.sh` come from Bazel

This change rewrites the four lines that hard-code `rules_yarn++yarn+npm`.
They now take the name from `bazel mod dump_repo_mapping ''`: the main
repository's mapping of apparent names to canonical names, read for the
apparent name `npm`. `site/en/external/module.md` (Bazel 9.2.0, the version
the script runs under through the root's `.bazelversion`) says canonical names
are "not an API you should depend on" and names that command as the supported
way to get them. This leaves the script no module name to carry.

## Risks / Trade-offs

- [Known limit] Two files carry the module name as a resolved label. A future
  rename, for instance back to `rules_yarn` if the registry agrees later,
  touches them as well as every consumer-facing example. If either is
  missed, `e2e/install` and `install_scenarios.sh` fail, because the
  generated repository loads both files.
- [Risk] Anyone on 0.1.0 through an override breaks on upgrade. Mitigation:
  the commit is marked breaking, and the README's migration note lists the
  edits. Those are the `bazel_dep` name, the override's `module_name` (also
  in any `--override_module` flag), and `@rules_yarn//` labels. The note also
  says that canonical repository names, and paths derived from them, change.
- [Risk] Between merge and tag push, main's README names a version that does
  not exist yet. Mitigation: task 5.2 pushes the tag right after the
  `tag.yaml` run that task 5.1 records.
- [Risk] The registry asks for a different name. Mitigation: under
  Decision 3's rule the rename is mechanical, and this design is the record
  for repeating it.

## Migration Plan

1. Land the change on main.
2. Dispatch `tag.yaml` once and record that it computes v1.0.0 and writes no
   tag (with the user's go-ahead).
3. Push the lightweight tag `v0.2.0` on the merge commit (with the user's
   go-ahead).
4. `release.yml` calls `publish.yaml`, which opens a draft pull request for
   `parkrevil_rules_yarn@0.2.0`. Mark it ready for review.
5. Close #10979, linking the new pull request.

Rollback: before step 3, revert the merge, and then push a release tag by
hand. A revert does not stop the `feat!` commit from counting: ccv stops
walking only at a tagged commit, so it keeps computing a major version, and
`tag.yaml` cuts no release until a person pushes a tag. After step 3, this
repository cannot withdraw a registry entry; fix forward with a new release.

## Defects the change review found, fixed here

The change review found two defects outside the rename. AGENTS.md says to
report such a defect and give it a change of its own. On 2026-11-19 the user
directed that both be fixed in this change so they ship with it. Decisions 7

### 7. A release refuses an annotated tag

`tag.yaml` leaves a major version to a person, but nothing said the tag must
be lightweight. ccv keys tags by the ref's own hash (`ccv.go:91-94` at
`7318e2f`), and an annotated tag's ref points at a tag object. ccv therefore
never sees such a tag, keeps counting the commits behind it, and holds every
later release at the version they call for.

`release.yml` gains a job, `lightweight-tag`, that `release` waits for. It asks
GitHub's "get a reference" API (`GET /repos/{owner}/{repo}/git/ref/tags/<tag>`)
for the ref's object type and fails, saying how to fix it, unless the type is
`commit`. Recorded responses:

| Tag | Type returned |
|---|---|
| `parkrevil/rules_yarn` `v0.1.0` (lightweight) | `commit` |
| `git/git` `v2.47.0` (annotated) | `tag` |
| a tag that does not exist | 404, and the step fails |

The step's commands, run against each in that order, exit 0, 1 and 1.

The second review ran ccv's own behaviour, building the pinned ccv in a scratch
repository after a `feat!` commit. Behind an annotated `v0.2.0` and a `fix`
commit, it computed `v1.0.0 major`. Behind a lightweight `v0.2.0`, it
computed `v0.2.1 patch`.

The command the notice, the error and the README give is
`git tag --no-sign <tag> <commit>`. A plain `git tag` signs the tag, which
makes it annotated, when `tag.gpgSign` is set. The flags `-a`, `-s`, `-u`,
`-m` and `-F` each make an annotated tag. Under `tag.gpgSign=true` (git
2.43), `git tag --no-sign` made a tag `git cat-file -t` reports as `commit`.
The error also gives the commands to delete the annotated tag locally and on
the remote first.

`tag.yaml`'s notice and summary for a major version, its header comment and
the README's Releases section now say to push a lightweight tag, and give the
command. `tag.yaml`'s own tags are lightweight already (`git tag "$TAG"` in a runner
with no `tag.gpgSign`).

**Alternatives considered:**

- **Documentation alone.** This relies on the person reading it, and the
  mistake surfaces only as releases that stop, days later. Rejected.
- **Changing ccv.** It is a pinned external action. Rejected.

[Known limit] The job first runs on GitHub at the v0.2.0 push (task 5.2).
Until then, its evidence is the local replay above together with GitHub's
documentation of the default shell, permissions in called workflows and the
preinstalled `gh`. If it fails there, a fix has to reach main before
`release.yml` can be dispatched again.

### 8. `install_scenarios.sh` prints the whole log of a Bazel command that stops it

The rule: a Bazel command whose failure stops the script keeps its output in
a log, and that whole log is printed before the script stops, through one
helper, `fail_with`, defined beside `die`. The rule is applied to:

- the Node.js build;
- `bazel info output_base` and `bazel info bazel-bin`, which are now asked
  once, since neither changes during a run (the per-call `b info … 2>/dev/null`
  in `built`, `layout_time`, `source_of` and the cycle case go);
- the `cquery` for Node.js's path;
- the canonical-name lookup.

The second review found that the cases' stopping points broke the same rule.
Seventeen `|| die "…$(tail -N log)"` sites printed only a tail of a log, and
eleven of them could print the wrong log. In `lock && pin || die
"…$(tail "$work/pin.log")"`, a failing `lock` printed the earlier run's
`pin.log`. In `lock && pin && build`, a failing `lock` or `pin` printed a
stale `build.log`. Now `lock`, `pin` and `build` each record their log in
`last_log`, and every such site calls `fail_with "$last_log"`. The three
`clean --expunge` sites and the plain `yarn install` call `fail_with` with
their own log. A simulated chain (`lock` fails after an earlier `pin`)
printed the stale `pin.log` with HEAD's script, and prints `lock.log` now.

The Node.js check now also requires a regular file. A failed `cquery` leaves
`node` as the output base, a directory, which `[ -x ]` accepts. A simulated
failure showed it passing silently before this change.

Verdict for the remaining `/dev/null` in the script, none of which is a Bazel
command on a failure path:

| Lines | What is discarded | Why it stays |
|---|---|---|
| 29-31 | errors from the exit trap's cleanup | best-effort cleanup after the run |
| 185 | `layout_time`'s `stat` | a missing layout is an answer the cases compare |
| 186, 498, 634 | `ls` and `readlink` probes | no match is the outcome under test |
| 343 | a `node -p` require probe inside one case | a mismatch is that case's `FAIL` |
